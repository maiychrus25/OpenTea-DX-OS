A digital operating system for tea cooperatives

Keep field journals, trace each tea lot back with its QR code, close the payment period for farming households and see the whole cooperative on one dashboard.

For developers: a headless core with single sign-on, an API gateway, data per cooperative and an audit log. Mini-apps are declared in an app.yaml file and installed with ./dxos install.

Why

One shared base for managers, officers and households

DX-OS aims to remove the information gap between the cooperative's management board, its technical officers and its farming households. It also brings the production cycle, from the plot and the journal to the lot, into one digital record that supports daily decisions.

Records scattered across places

Journals, weighing tickets, orders and attendance are often kept in separate books. When a period closes, someone has to piece them together by hand. DX-OS keeps them in one database owned by the cooperative.

Traceability needs the right links

Each lot gets a QR code and a certificate. The project digitises the production chain, from the plot and the field journal to the lot.

Apps that share one core

Every app uses the same sign-in, the same role checks and the same data, filtered by cooperative. Adding a tool means installing a mini-app. The core does not change.

Architecture

Three tiers, one core

The shared core sits at the bottom. Cooperative apps are in the middle. Installed mini-apps are at the top and reach the core through the API gateway. Nothing in the core depends on any app.

Tier 1

Shared core

  • Single sign-on with Keycloak and three roles: manager, technical officer, farming household.
  • Hasura serves read-only data filtered by the cooperative code in the token, so users see their own cooperative's data.
  • Sensor readings arrive over MQTT, sit in a hot store and move to a Parquet cold store.
  • Audit log as a hash chain, with a command that verifies its integrity.
  • Files in storage are scanned with ClamAV; infected or unscannable files are quarantined.

Tier 2

Cooperative apps

  • Next.js web app: field journal, parcel map, lots and QR codes, audio news bulletins.
  • Tea leaf disease check from a photo. Every result goes to the technical officers' queue.
  • Staff desktop (WPF, Windows) and staff mobile (Android) for staff, tasks and attendance.
  • Hub mobile (Flutter) is in development and not yet released.

Tier 3

Installed mini-apps

  • Declared with app.yaml, installed with ./dxos install.
  • Each cooperative turns apps on in the App Store and sees them in its own menu.
  • Each runs in a locked-down container; its pages contain no JavaScript.
  • Seven apps ship in the repository, including the no-code record book builder.
Features

What a cooperative can do today

The images below are screenshots of the apps in the repository, with sample data. Where a group has no screenshot in the repository, the page says so.

Fresh leaf purchase and payment periods

Officers record each household's weighing tickets by tea type. The manager follows the kilograms of the day and the month, closes a payment period and prints the statement.

  • Input errors appear right under the wrong field, and typed text is kept.
  • Overview: kilograms, amount still unpaid and a 14-day chart.
  • Close the period, print the statement, download CSV, record each household as paid.
  • A household sees its own tickets and payments.
mini-app leaf-purchase 0.2.0

A digital profile for each plot

Each plot has a summary page: sensor readings by day, weather, the current crop cycle, journal entries, disease reports and the lots that use the plot. The manager dashboard shows the whole cooperative on one screen.

  • Items needing attention: journals waiting more than 3 days, disease reports waiting, sensors silent for more than 6 hours.
  • Figures with change from the previous period, plot status donut, area by crop.
  • Read-only: the app stores nothing, and each figure is read from the core with the viewer's own permissions.
mini-app htx-dashboard 0.2.0

Shop, group supplies and tours

Three mini-apps help a cooperative sell and organise. Customers need no account to order or book; a customer's personal details are visible only to the manager of that cooperative.

  • Tea shop: customers order and pay on delivery; orders are tracked with the order code and phone number.
  • Group supplies: open a sign-up round, mark each household delivered and paid, print a delivery sheet with signature column.
  • Tea hill tours: bookings, check-in and a printable list of each group.
mini-apps tea-shop, farm-supply, tea-tour 0.2.0

Record books without code

A manager starts from one of eight templates, such as picking attendance, spraying log, cash book or a blank book, then names the fields and sets who can use the book.

  • Eight field types: text, long text, number, money, date, choice, yes/no, household.
  • Separate access for officers and farming households, with optional approval of each row.
  • Monthly summary, CSV download and printing.
mini-app custom-books 0.1.0

Staff, tasks and attendance

The cooperative owner manages staff on a Windows computer. Staff accept tasks, report progress, clock in and out and request leave on an Android phone. Data reaches the owner's computer over the local network.

  • Staff desktop: staff records, teams, task assignment, attendance, leave approval and payroll.
  • Staff mobile: tasks to do, clock in and out, leave requests, payslips.
apps/staff-desktop, apps/staff-mobile

Trace a lot with its QR code

Each lot that has a QR code has a public traceability page showing the lot's QR code, the product, the cooperative and the plot the lot came from.

  • Confirmed and locked information: the data does not change after the lot's QR code is issued.
  • The origin is linked to the farming household's plot.

The field journal and the tea leaf disease check have no screenshots in the repository yet; this page does not use stand-in images.

web app, public lot traceability page

Install mini-apps from the App Store

The cooperative manager installs and removes mini-apps in the App Store. Each cooperative turns apps on for itself; an app card changes from Not installed to Installing… and then Installed.

  • Removing an app only turns it off for the cooperative and keeps the data; the app is removed from the server only when the last cooperative has turned it off.
  • Each app's page shows its screenshots, the data the app stores and the personal data it declares.
  • The Install and Remove buttons work only while the ./dxos worker process is running.

Developers

Add a mini-app without changing the core

A mini-app is its own container, plugged into the core with a manifest and the ./dxos command. The core is not rebuilt. The example below is the real manifest of miniapps/htx-dashboard, with the store description block removed.

# miniapps/htx-dashboard/app.yaml (shortened)
apiVersion: dxos/v1            # manifest schema version, fixed
id: htx-dashboard             # unique among installed apps
name: Bảng điều hành HTX     # shown to users
version: 0.2.0                # SemVer
license: MIT
requires: { core: ">=1.13.0" }  # minimum core version
runtime:
  build: .                    # build from the app folder, or a pinned image
  port: 8080                  # port the app listens on in its container
  health: /healthz            # must return 2xx
routes:
  protected:
    /: [manager]              # path → roles allowed
menu:
  - { label: Bảng điều hành, path: /, roles: [manager] }

Install command, after make platform-up and make web-up:

./dxos install miniapps/htx-dashboard

One install checks the manifest, creates the database schema and role if the app declares them, generates the gateway routes and starts the container. If a step fails, the earlier steps are rolled back.

  • Locked-down containerNo host port, read-only file system, all Linux capabilities dropped, 256 MB of memory, 0.5 CPU and an internal network with no internet access.
  • Cooperative data comes from the tokenEvery query is filtered by the cooperative code in the token, never by a URL or form value. Each page still checks the role.
  • Trust boundary, with a known limitInstalled apps share one internal network and can call each other. Install only trusted apps. The docs list this as a known limit.

Run from source

Requires Docker and Docker Compose v2. The full stack has 16 containers and uses about 3.6 GiB of RAM.

cp .env.example .env.local cp docker/.env.local.example docker/.env.local docker compose -f docker/docker-compose.yml up -d bash scripts/smoke-test.sh

To use mini-apps, run make platform-up (or make up) instead of the bare docker compose command, which loads no app routes. Web app: http://localhost:3000.

Status

Current version and known limits

This section lists only what the repository documents. Version numbers come from apps/web/package.json, CHANGELOG.md and the GitHub release tags.

Core version in source: 1.13.0 Latest release: v1.12.0 (14 Nov 2026) Not yet released: staff apps, hub mobile, htx-dashboard 0.2.0

Known limits

  • Tea leaf disease check: accuracy is 0.87 on a test set from the same source, but only 0.12 to 0.35 when checked across image sources. Accuracy on Thai Nguyen tea photos has not been measured. Every result, including healthy leaves, goes to the officers' queue.
  • File storage: the /storage/* route does not yet verify S3 SigV4 signatures; this waits for tier 2.
  • Mini-apps: installed apps trust each other over one internal network; per-app isolation is not built yet. The public pages of mini-apps allow 10 requests per minute per IP, counted inside each process.
  • Record books: no image or file fields, no formulas, one approval step; each cooperative can have at most 50 books and each book at most 20 fields.
  • Sensors: Mosquitto saves its state to disk every 60 seconds, so messages queued in the last 60 seconds can be lost if the broker crashes.
  • Desktop staff app: built for Windows only; building it needs the .NET 10 SDK.
